# scope\n* Project Objective: Migrate the Enterprise Data Warehouse (EDW) from on-premise Teradata to Google Cloud Platform (BigQuery), specifically focusing on Wave 2 in multiple tracks.\n* Track 0: Eagle Data Warehouse Assessment\n * Discovery and Analysis: Understand technical/functional requirements, current state architecture, tools, source/downstream application patterns, workload distribution, data flow lineage, Teradata scripts lineage, unused/redundant tables, volumetrics, complexity, challenges, and gaps.\n * Design & Recommendations: Provide BigQuery Technical and Solution Architecture, migration scope/strategy, plan, approach, and estimates.\n* Track 1A, 1B, 1C:      Modernisation\n * Track 1A: Migrate Bookings (excluding Near Real-Time bookings).\n * Track 1B: Migrate Revenue (all related measures) and Expense.\n * Track 1C: Migrate all non-financial measures.\n * Convert Teradata Table/View DDLs to BigQuery DDLs.\n * Refactor in-scope Informatica jobs to equivalent DBT (using incremental files in GCS provided by Cisco).\n * Migrate historical data from GCS to BigQuery.\n * Set up orchestration and scheduling using DBT and Control-M.\n * Convert existing reporting views in the BigQuery consumption layer.\n * Deliver exports based on agreed-upon discovery phase specifications.\n * Perform testing, end-to-end pipeline and unit testing, and data validation using Datametica Pelican.\n * Execute production deployment, handover, knowledge transfer, and provide 3 months of Parallel Run support.\n* Track 1A, 1B, 1C: Optimization\n * Identify underperforming DBT scripts in collaboration with Cisco.\n * Perform root cause analysis of identified code.\n * Design, recommend, and implement solutions to improve performance based on GCP/Datametica best practices.\n * Retest optimized scripts against Cisco benchmarks.\n* Volumetrics (Tracks 1A, 1B, 1C)\n * Tables (Final Layer): Track 1A (800), Track 1B (900), Track 1C (1,100).\n * Tables (Intermediate): Track 1A (4,200), Track 1B (4,500), Track 1C (5,700).\n * Views: Track 1A (240), Track 1B (270), Track 1C (330).\n * Informatica Jobs (ELT): Track 1A (2,800), Track 1B (3,000), Track 1C (3,800).\n\n# out_of_scope\n* Wave 1: Recurring revenue metrics (AOV, iACV, and Common hierarchies) modernization.\n* Wave 3: Finance dashboards, including Business Objects universes, Microstrategy dashboards, and data extracts.\n* Wave 4: Non-Finance dashboards, including required data excluded from Wave 2.\n* Staging layer/landing zone setup, ingestion, historical data migration, and staging table/jobs conversion or optimization.\n* Consumption Application scope (performed by Cisco).\n* Any additional Teradata scripts, Stored Procedures, or functions not driven by the provided ETL scripts.\n\n# success_criteria\n* Successful implementation and sign-off of the design solution for optimized DBT scripts from the Cisco team within five days of delivery.\n* Successful completion of User Acceptance Testing (UAT) by the Cisco team within five business days after delivery.\n* 100% reconciled and validated data using Datametica Pelican.\n\n# assumptions\n* Google Cloud foundation is already in place.\n* Network connectivity between Teradata and GCP is already set up.\n* The staging layer/landing zone is already in place and requires no efforts for ingestion or conversion.\n* All processing and transformation are driven by provided ETL scripts only.\n* The total number of in-scope intermediate tables is 1.5 times Informatica ETL.\n* The total number of in-scope views is 30% of final layer tables.\n* Datametica will absorb volumetrics changes up to 5%.\n* Cisco will provide:\n * Execution of extraction utility and output shared with Datametica.\n * In-scope data in the GCS bucket within the GCP environment.\n * Access to GCP (dev and prod), Teradata environment, artifacts, data/mapping, VDI/VPN, and infrastructure/security clearance at no cost.\n * Required data/documents/knowledge transfer associated with in-scope systems.\n * A technical & functional Point of Contact (SME).\n * Timely sign-offs, reviews of documentation, decisions, and designs.\n * User onboarding, environment creation, service enablement, and BQ Slots procurement.\n\n# deliverables\n* Eagle Assessment Artifacts:\n * Volumetric Metadata vs logs (Active).\n * Workload Distribution Dashboard.\n * Active Objects granular details.\n * Upstream and Downstream Pattern (Direct Load and Extract to Database).\n * Data Flow Lineage (End-to-End, N-Level View, View to Base Tables).\n * Code & Workflow Lineage (Teradata scripts lineage, Code complexity analysis).\n * Insights (Important/popular tables, Data Modeling join analysis, Active User Session Analysis, Custom Tagging).\n* Modernization Artifacts:\n * BigQuery DDLs (converted from Teradata).\n * Refactored DBT scripts (converted from Informatica).\n * Configured orchestration and scheduling (DBT and Control-M).\n * Converted reporting views in BigQuery.\n * Data exports based on specifications.\n * Data validation reports generated by Datametica Pelican.\n* Optimization Artifacts:\n * Root cause analysis and design solutions for underperforming DBT scripts.\n * Retested and optimized DBT scripts.\n\n# solution_overview\n* Migration Approach: Fixed Price and Time agile delivery model spanning a 16-month timeline. Focuses on assessment, code conversion, data reconciliation, and cloud optimization using Datametica's automated product suite.\n* Datametica Birds (Automation Suite):\n * Eagle (The Planner): Drives discovery, assessment, holistic workload views, data lineage, and cloud optimization (anti-pattern recognition).\n * Raven (The Transformer): Automates code (ETL/SQL) conversion to cloud-native technologies (e.g., Informatica to DBT).\n * Pelican (The Validator): Automates cell-level data validation, reconciliation, and heterogeneous dataset comparison without data movement.\n* Architecture Pattern: Data moves from Source Systems to BigQuery Staging (performed by Cisco), then processed using DBT into BigQuery Processing and Consumption layers (Datametica scope).\n* Optimization Strategy:\n * Implement optimal BigQuery structure with Partitions and Clusters derived from usage patterns.\n * Execute metadata-driven code conversion and parallelize workflows based on intrinsic dependency.\n * Retire workflows for cold objects.\n * Utilize FinOps services to optimize GCS Storage, BigQuery Storage, and BigQuery Slots.\n* Delivery Model: Onshore/Offshore model led by Technical Project Managers and Architects, utilizing specialized pods of Data and Test Engineers, supported by a 3-month Warranty/Parallel Run phase."
